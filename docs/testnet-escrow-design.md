# 테스트넷 에스크로 설계안

상태: **제안 · Foundry 및 로컬 Anvil 시험 구현** · 근거: `Crypto_P2P_Dex_PRD_v1.0.docx`의 ORD-01~07, 4.1절, D-01~06. 계약 코드는 [`contracts/src/PeerEscrow.sol`](../contracts/src/PeerEscrow.sol), 상태 전이 테스트는 [`contracts/test/PeerEscrow.t.sol`](../contracts/test/PeerEscrow.t.sol)에 있다. 체인·실제 토큰 주소·운영 주체·수수료·중재 권한은 출시 결정이 아니다.

## 범위와 임시 가정

- 단일 EVM 체인에서 두 개의 **사전 승인된 일반 ERC-20**을 교환한다. 기존 화면의 `ETH`는 온체인 예치 시 WETH로 표시·변환해야 한다. 네이티브 ETH, 네이티브 BTC, 크로스체인, 수수료형·리베이스 토큰은 이 계약 범위에서 제외한다. Sepolia는 현재 로그인 검증 체인이며 테스트넷 후보일 뿐이다.
- 주문별 순서는 **Maker 선예치 → Taker 후예치**로 가정한다. 광고 등록 자체를 선예치로 간주하지 않는다. 광고의 실제 담보와 잔액은 별도 확인해야 한다.
- Taker의 예치 트랜잭션 안에서 두 자산을 **즉시 원자적으로 정산**한다. 양측이 예치한 채 별도의 `settle` 호출을 기다리는 상태는 두지 않는다. 한쪽만 예치한 경우 상대방 기한 경과 후 Maker가 환불받는다.
- 테스트넷 기본 창은 계약 개설 후 Maker 예치 15분, Maker 예치 후 Taker 예치 15분이다. 각 기한은 체인 시간(`block.timestamp`)을 기준으로 하며, 기한 **이하**에 예치 가능하고 기한 **초과**에 만료·환불 가능하다. UI 시계는 안내용이다. 이 값은 사용자 시험 후 확정한다.
- EOA 지갑의 주문별 EIP-712 서명을 사용한다. SIWE 로그인 세션이나 서버의 광고주 수락 클릭은 자금 이동 동의로 보지 않는다. 계약 지갑 ERC-1271 지원은 별도 설계 과제다.

## 고정 약정과 자금 흐름

서버는 예약 시 광고 버전과 정수 단위 견적을 고정한다. Taker는 해당 약정을 주문별로 서명하고 Maker는 수락 시 **동일한 약정**을 서명한다. `openOrder`는 두 서명을 검증한다. 광고 변경, 세션 탈취 또는 서버의 상태 변경만으로 계약 약정을 바꿀 수 없어야 한다. 화면은 사용자가 서명할 토큰 **주소·체인·수량·수취인·수수료·기한**을 보여 준다.

EIP-712 도메인에는 이름/버전, `chainId`, 배포된 계약 주소를 넣는다. 서명 데이터에는 무작위 32바이트 `orderId`, Maker/Taker 주소와 각자 nonce, 두 토큰 주소, 각 예치량과 수취량, 수수료 토큰/수량, 서명 유효기한을 넣는다. 서명 유효기한은 서버의 수락 후 개설 기한을 넘지 않는다. `orderId`와 nonce는 계약에서 재사용할 수 없으며, 당사자는 `invalidateNonce`로 아직 개설되지 않은 서명을 폐기할 수 있다. 서버의 취소 클릭만으로 서명된 주문을 무효화할 수는 없으므로 개설 전 취소 UX는 서명자 중 한 명의 nonce 폐기 확인 또는 서명 기한 경과를 포함해야 한다. 현재 데모의 UUID와 JSON SHA-256 `terms_hash`는 온체인 EIP-712 해시와 호환되지 않으므로 새 주문 형식으로 전환해야 한다.

`makerToken != takerToken`, 각 예치량 > 0, 토큰 allowlist, 수수료 토큰 = 두 교환 토큰 중 하나인 USDC, 고정 treasury와 수수료 상한을 계약이 검사한다. 수수료 상한은 서명된 수수료 제외 USDC 금액을 기준으로 `fee <= ceil(usdcAmount * maxFeeBps / 10_000)`처럼 정수로 검사한다. 수수료는 실제 체결 때만 treasury로 지급하며, 계산·반올림이 끝난 **토큰 최소 단위 정수**를 두 지갑이 서명한다. 예치와 지급의 보존식은 다음과 같다.

| 수수료가 포함된 예치 토큰 | 예치량 검증 | 최종 지급 |
| --- | --- | --- |
| Maker가 USDC 예치 | `makerDeposit = takerReceive + fee` | Taker에게 `takerReceive`, treasury에 `fee`; Taker 예치 전량은 Maker에게 |
| Taker가 USDC 예치 | `takerDeposit = makerReceive + fee` | Maker에게 `makerReceive`, treasury에 `fee`; Maker 예치 전량은 Taker에게 |

예: Taker가 WETH 0.4개를 1,000 USDC에 **구매**하고 수수료가 1 USDC면 Maker는 WETH 0.4개, Taker는 USDC 1,001개를 예치한다. 정산 시 Maker는 USDC 1,000개, Taker는 WETH 0.4개, treasury는 USDC 1개를 받는다. Taker가 WETH 0.4개를 **판매**하면 Maker는 USDC 1,000개, Taker는 WETH 0.4개를 예치하고 정산 시 Taker가 USDC 999개, treasury가 USDC 1개를 받는다. 이는 현재 화면의 구매 수수료 추가·판매 수수료 차감 표시와 일치한다. 예시 0.1% 요율은 출시 요율 결정이 아니다.

## 계약 상태 전이

| 현재 상태 | 호출·조건 | 다음 상태 | 자금 결과 |
| --- | --- | --- | --- |
| 미개설 | `openOrder(terms, makerSig, takerSig)` · 두 서명 유효·nonce 미사용 | `OPEN` | 없음. Maker 기한 시작 |
| `OPEN` | `depositMaker` · Maker만·기한 이하·정확한 토큰/수량 | `MAKER_FUNDED` | Maker 자산 잠금. Taker 기한 시작 |
| `OPEN` | `cancelUnfunded` · 당사자 중 한 명 | `CANCELLED` | 없음 |
| `OPEN` | `expireUnfunded` · Maker 기한 초과 | `EXPIRED` | 없음 |
| `MAKER_FUNDED` | `depositTaker` · Taker만·기한 이하·정확한 토큰/수량 | `SETTLED` | Taker 예치, 양측 지급, 수수료 지급이 한 트랜잭션에서 성공 |
| `MAKER_FUNDED` | `refundMaker` · Taker 기한 초과 | `REFUNDED` | 잠긴 Maker 자산을 Maker에게 전액 반환 |
| 종료 상태 | 모든 상태 변경 호출 | 오류 | 중복 지급·환불 없음 |

`depositTaker`의 어느 이체라도 실패하면 **트랜잭션 전체가 되돌아가고** 상태는 `MAKER_FUNDED`다. 그 전에는 상대방에게 지급할 수 없다. `refundMaker`는 누구나 호출할 수 있지만 수취인은 약정된 Maker로 고정된다. Taker는 이 설계에서 정산과 같은 트랜잭션 안에만 예치하므로 별도의 Taker 환불 잔액은 생기지 않는다. 기한 직전 `depositTaker`와 직후 `refundMaker`가 경쟁하면 체인에 먼저 포함되어 조건을 만족한 한 경로만 성공한다.

`OPEN` 상태의 취소는 자금이 없을 때만 허용한다. `MAKER_FUNDED` 이후 즉시 취소·운영자 임의 지급·분쟁 판정은 이 테스트넷 계약에 넣지 않는다. 계약에 정지 기능을 둔다면 새 주문·예치만 막고 `expireUnfunded`·`refundMaker` 및 nonce 폐기는 계속 허용해야 한다. 정지·업그레이드·중재 권한을 실제 운영에 넣을지는 D-01/D-05 결정 후 별도 검토한다.

## 구현 경계와 불변조건

1. `openOrder`는 allowlist 토큰·현재 체인, 정확한 EIP-712 서명, 미사용 `orderId`와 nonce, 유효한 미래 기한, 수수료 보존식·상한을 검사한다. 서명 만료 뒤에는 서버가 `ACCEPTED`라고 표시해도 열 수 없다.
2. `depositMaker`와 `depositTaker`는 `SafeERC20`과 재진입 방지를 사용한다. 허용 토큰의 `balanceOf` 증가량이 기대 예치량과 정확히 같은지 확인해 수수료형 토큰을 거부한다. 상태를 외부 이체보다 먼저 갱신하되 실패 시 전체 롤백한다.
3. 주문별 자산 지급은 `SETTLED` **한 번**, 환불은 `REFUNDED` **한 번**만 가능하다. 두 종료 경로는 배타적이다. 어느 시점에도 계약의 토큰별 잔액은 활성 주문에 잠긴 총액 이상이어야 한다. 계약 관리자에게 주문 잔액을 임의 인출하는 함수는 두지 않는다.
4. allowlist는 코드·배포 설정과 UI에서 동일한 **주소**로 관리한다. 심볼만으로 식별하지 않는다. 토큰의 블랙리스트·일시정지·프록시 변경은 환불 자체를 실패시킬 수 있으므로, USDC 포함 후보 토큰을 실사하고 장애 정책을 별도로 정해야 한다. 수동 ERC-20 직접 전송은 주문 예치로 인식하지 않는다.
5. 이벤트는 `OrderOpened`, `MakerDeposited`, `OrderSettled`, `OrderCancelled`, `OrderExpired`, `MakerRefunded`, `NonceInvalidated`에 `orderId`를 포함한다. 지급 금액·토큰·수취인은 이벤트 또는 불변 약정으로 재구성 가능해야 한다. 이벤트는 계약 상태의 증거이며 서버의 임의 `COMPLETED` 변경 API는 두지 않는다.

## 현재 로컬 체인 구현과 운영 전 변경

로컬 시험에서는 `31337` Anvil 체인에만 배포할 수 있다. 수락된 ETH 데모 주문을 별도의 `chain_orders` 약정으로 전환하고, 양측 EIP-712 서명을 저장한다. 지갑에서 승인·개설·예치·취소·환불을 직접 보내며, 서버는 확인된 계약 로그를 읽어 주문 상태와 광고 재고를 투영한다. SQLite에 블록 체크포인트를 저장하고 이후의 로그만 이어 읽으며, 재구성 시 공통 체크포인트부터 다시 계산한다. RPC 오류가 나면 저장 상태를 유지한다. 서명 기한 경과 후에는 체인 시각과 `getOrder`의 미개설 상태를 확인한 뒤 재고를 해제한다. [`tests/chain-e2e.ts`](../tests/chain-e2e.ts)가 정산·취소·환불·재구성과 10,000블록 이상 지난 뒤 동기화를 검사한다.

운영 전에는 다음 변경이 필요하다.

- 지금의 `RESERVED → ACCEPTED → EXPIRED`는 **데모 예약**이다. 자금이 예치된 온체인 주문에 현재 `ACCEPTED`의 15분 자동 만료·잔량 복구·거래자 취소 로직을 적용하면 안 된다. 서명 후 개설 트랜잭션이 전송되면 `OPEN_PENDING`으로 예약 수량을 유지한다. 서버 기한이 지나도 보류 트랜잭션이나 인덱서 지연 가능성이 있는 동안은 잔량을 재배정하지 않는다. 개설 실패·서명 만료를 체인과 대조한 뒤에만 해제한다. 온체인 `OPEN/MAKER_FUNDED` 후 광고 잔량은 확정된 계약 종료 이벤트를 반영할 때만 해제하고, `SETTLED`면 판매량으로 확정한다.
- 운영 저장소에는 예약/서명 상태와 체인 상태를 분리하고 `chainId`, 계약 주소, `orderId`, 약정 해시, 서명 만료, 예치·환불/정산 tx hash, 블록 번호/해시/로그 인덱스, 확인 수를 보존한다. 로컬 시험의 SQLite 데모 주문 승격 모델을 운영 거래에 그대로 사용하지 않는다. 운영용 원자적 예약·이벤트 로그는 PostgreSQL 전환 시 설계한다.
- 운영 인덱서는 `(chainId, txHash, logIndex)`로 이벤트를 멱등 처리하고 블록 해시와 부모 연결을 검사한다. reorg 시 기준 블록부터 재생해 계약 `getOrder`와 대조하고, RPC 장애 중에는 체인 상태를 확정 표시하지 않는다. 로컬 시험 인덱서의 체크포인트 복구를 운영에 적용하려면 다중 프로세스 동시 동기화와 최종성 정책을 체인 선택 후 검증해야 한다.
- 지갑은 지원 체인·토큰 주소·잔액·가스·**정확한 예치량의 allowance**를 표시하고 사용자가 직접 `approve`와 예치를 서명한다. 로컬 시험 UI는 토큰·수량·잔액·승인과 현재 RPC 기반 가스비 견적을 표시한다. 운영 전에는 실제 체인의 수수료 모델과 실패 복구 UX를 다시 검증해야 한다. 무제한 승인을 기본값으로 두지 않는다.

## 구현 전 검증과 결정

Foundry 테스트는 정상 양방향 교환, 서명 재생/nonce 폐기, 잘못된 토큰·체인·서명, deadline 경계, 단방 예치 환불, 이중 정산/환불, 재진입 시도, 수수료형 토큰, 이체 실패, 정지 중 환불과 동시 주문 잠금액을 검증한다. 퍼즈 테스트는 수수료와 거래 방향에 따른 자산 보존을 검증한다. 별도의 상태 기반 불변조건 캠페인과 토큰·서명 경계 확대 검증은 남아 있다. 인덱서 테스트는 중복 이벤트·재시작·reorg·RPC 장애 복구를 포함해야 한다. 테스트넷 E2E는 두 지갑의 승인부터 주문 생성, 두 예치, 확정된 정산/환불과 UI 이력까지 확인해야 한다. 보안 감사 전 실제 가치가 있는 자산을 취급하지 않는다.

| PRD 결정 | 구현 전 필요한 답 |
| --- | --- |
| D-01/D-05 | 정지·업그레이드·중재 권한과 키 보관, 자금 잠금 중 개입 가능 범위 |
| D-03 | 실제 단일 체인, 체인별 확인 블록 수, 토큰 주소·관리자 권한·동결 가능성 실사 |
| D-04 | Maker 선예치와 각 예치 기한을 제품 정책으로 채택할지, 광고 담보를 어떻게 검증할지 |
| D-06 | 실거래 수수료율·상한·수취 주소, 최소 단위 반올림·dust·가스 부담 |

국가·법인·KYC/제재 범위(D-02/D-07)와 광고 신뢰 정책(D-08)도 테스트넷 외 실제 운영 전에 별도로 결정해야 한다.
