# Phase 0 — 제품 및 구현 범위

근거: Crypto_P2P_Dex_PRD_v1.0.docx (2026-10-22). 문서는 요구사항과 설계 제안으로 검토했다. 문서의 후보 기술과 미확정 정책은 출시 결정으로 간주하지 않는다.

## 첫 번째 개발 결과

Next.js App Router + TypeScript 단일 웹 앱. MKT-01/02의 데모 광고 목록, 구매/판매, ETH/WBTC 선택, USDC 기준 금액 검색, 가격순 정렬, 빈 결과, 광고 상세 및 정수 기반 견적을 제공한다. 입력은 USDC 소수점 6자리까지 허용하고 자산 수량은 내림, 예시 수수료 0.1%는 micro-USDC 단위 올림한다. 판매 견적은 수수료 차감 USDC 수취, 구매 견적은 수수료 포함 USDC 지급을 표시한다.

두 번째 개발 결과: Sepolia EOA 서명 로그인(SIWE), 로컬 SQLite 저장소, 공개 광고 API, 로그인 사용자 전용 데모 예약·조회·취소 API. 서버는 가격과 잔량을 재검증하고 트랜잭션으로 예약한다. 15분 만료 또는 취소 시 잔량을 복구한다. 주문 키 멱등성, nonce 일회성, 출처 검사, HttpOnly 세션을 적용했다. SQLite는 단일 인스턴스 개발용 저장소다. Sepolia는 지갑 로그인 검증용이며 출시 체인 결정이 아니다.

세 번째 개발 결과: 로그인한 광고주가 데모 광고를 등록·수정·일시중지·재개·종료하고 1~168시간 유효기간을 설정할 수 있다. 광고주 지갑 소유권, 버전 충돌, 예약 수량 보호, 기존 주문 약정 보존을 서버에서 검사한다. 테스트 데이터에서 실제 자산 담보 여부는 검증하지 않는다.

네 번째 개발 결과: 광고주가 자신의 데모 주문을 수락·거절하고 거래자와 함께 상태 이력을 조회한다. 예약의 광고주 응답 기한은 광고별 5~60분이며, 수락 시 15분의 데모 종료 기한이 새로 시작된다. 거절·취소·만료는 광고 잔량을 한 번만 복구한다. 기존 SQLite 주문은 상태와 잔량을 보존하며 이전 시점의 상태 이력을 한 건 남긴다. 연결된 광고주 지갑이 없는 예시 광고는 수락할 수 없어 응답 기한에 만료된다.

다섯 번째 개발 결과: 수락된 ETH 데모 주문을 로컬 Anvil WETH/USDC 주문으로 전환한다. 양측 EIP-712 서명, 지갑의 토큰 잔액·allowance 확인과 승인, Maker 예치·Taker 원자적 정산, 취소·환불을 시험할 수 있다. 서버는 확인된 계약 로그로 상태·광고 재고를 투영하고 체인 재구성에서 되돌린다. 서명 만료 시 온체인 미개설을 확인하고 재고를 복구한다.

여섯 번째 개발 결과: Playwright의 두 독립 브라우저 세션으로 지갑 로그인부터 광고·주문·에스크로 정산까지 검증한다. 지갑 서명 거절과 확정 실패 거래의 재시도, 영수증 확인이 지연된 거래의 브라우저 새로고침 복구를 확인한다. 화면은 미확인 거래의 해시를 보존하고 재전송 버튼을 잠근다.

일곱 번째 개발 결과: 양쪽 주문 화면에 참가자 전용 대화와 주문 상태 알림을 추가했다. 3초 폴링으로 새 메시지를 표시한다. 메시지는 1000자·주문당 500건·발신자별 2초 간격으로 제한하고 요청 ID로 중복 등록을 막는다. 종료된 주문은 읽기 전용이다. 로컬 SQLite에 평문으로 저장되며 개발 프리뷰에서는 주문 종료 30일 후 삭제한다. 운영 암호화 정책은 결정되지 않았다.

여덟 번째 개발 결과: 주문 참가자별 상대방 신고·차단을 추가했다. 신고는 주문당 한 건으로 제한하고 검토 대기 상태로 저장한다. 차단은 서로의 새 광고 예약을 서버에서 막고 로그인 광고 목록에서 숨긴다. 기존 주문과 자산 회수는 계속할 수 있다. 평판·후기는 MVP에서 제외하고 가상의 거래 건수·완료율 표시와 완료율 정렬을 제거했다. 기존 SQLite 광고 테이블의 두 칼럼은 마이그레이션 호환용으로 남지만 API는 반환하지 않는다.

아홉 번째 개발 결과: 개발 프리뷰의 대화는 주문 종료 30일, 신고는 180일 후 삭제한다. 종료 30일 후 새 신고 접수를 닫는다. 주문 조회 시 만료 기록을 지우고, `npm run data:prune`으로 접근하지 않은 주문도 정리한다. 상태 이력과 사용자 차단은 별도 보존 대상이며, 운영 보존·법적 예외 정책은 아직 결정되지 않았다.

열 번째 개발 결과: 환경 변수에 허용한 SIWE 지갑만 신고 검토 화면과 API에 접근한다. 운영자는 신고 상세·주문 이력·보존 중인 대화를 보고 ‘확인됨’ 또는 ‘기각’ 결과와 메모를 한 번 기록한다. 신고 당사자는 결과를 확인하지만 운영자 메모는 볼 수 없다. 심사로 계정을 자동 제재하거나 온체인 자금을 옮기지 않는다. 증빙 업로드와 정식 이의 제기·운영자 권한 관리 정책은 미구현이다.

열한 번째 개발 결과: 로컬 체인 지갑 거래는 전송 전에 `eth_estimateGas`와 `eth_gasPrice`로 예상 ETH 비용을 보여주고 별도 확인을 받는다. 견적 실패·1분 경과·주문 상태 변경 시 전송을 멈춘다. 실제 지갑의 최종 수수료는 달라질 수 있으며 운영 체인 수수료 정책은 미결정이다. 이의 제기는 MVP에서 제외한다.

열두 번째 개발 결과: 예약자와 광고주의 거래 목록에 전체·진행 중·완료·종료/환불 필터와 상태별 건수를 추가했다. 상태 이력은 변경 주체와 시각을 보여준다. 필터 선택은 목록을 새로고친 뒤에도 유지된다. 영수증 화면과 CSV 내보내기는 MVP 범위에서 제외한다.

열세 번째 개발 결과: 광고 탐색에 유리한 가격순과 거래 가능 수량 많은 순 정렬을 제공한다. 수량은 ETH/WBTC의 실제 소수점 정밀도로 비교하고, 같은 수량에서는 유리한 가격을 우선한다. 거래 금액 필터와 조합해도 정렬 기준을 유지한다. 위험 안내와 FAQ는 MVP에서 제외한다.

열네 번째 개발 결과: 광고 탐색에 최근 등록순 정렬을 추가했다. 새 광고는 등록 시각과 순서를 저장하고, 수정해도 원래 등록 순서를 유지한다. 기존 광고는 알 수 없는 등록 시각을 채우지 않고 기존 저장 순서로 마이그레이션한다. 동일 시각의 광고는 등록 순서로 비교한다.

열다섯 번째 개발 결과: 두 독립 웹 서버가 한 SQLite DB를 공유하도록 구성해 광고 잔량 예약 경합을 HTTP 통합 테스트로 검증했다. 4개 지갑이 동시에 주문하는 16회 시험에서 광고별 허용 수량인 1건 또는 2건만 생성되고, 두 서버의 잔량·주문 수가 일치했다. 성공 요청의 키를 반대 서버에서 재전송해도 같은 주문을 반환했다. 이 시험은 로컬 DB 예약의 원자성을 검증하며, 운영 DB나 온체인 계약의 동시성 검증을 대체하지 않는다.

열여섯 번째 검증 결과: 임시 Anvil·SQLite에서 Maker 예치 후 웹 서버를 종료하고 같은 DB로 재시작했다. 저장된 체크포인트와 주문 상태가 복구됐으며 새 Taker 정산 로그도 반영됐다. 같은 상태에서 동기화를 세 번 반복하고 체크포인트 삭제로 전체 로그 재처리를 강제해도 이벤트 3건, 정산 상태 이력 1건, 광고 잔량·버전이 유지됐다. 이 시험은 로컬 개발 인덱서의 재시작·중복 읽기 검증이다.

열일곱 번째 검증 결과: 로컬 RPC 프록시를 차단한 상태에서 명시적 동기화와 주문 조회가 503을 반환하며 저장된 주문·재고·체크포인트를 변경하지 않는지 확인했다. 차단 중 정산 거래를 체인에 발생시킨 뒤 연결을 복구하자 누락된 로그를 읽어 정산 상태와 광고 잔량을 한 번만 반영했다. 로컬 개발 인덱서의 일시적인 RPC 장애에 대한 시험이며 운영 장애 대응 정책의 검증은 아니다.

열여덟 번째 개발 결과: 두 웹 서버가 한 SQLite DB와 같은 Anvil 체인을 공유하는 경합 시험에서 이전 블록을 읽은 서버의 늦은 스캔이 먼저 반영된 정산을 `MAKER_FUNDED`로 되돌리는 결함을 재현했다. 인덱서가 스캔 중 체인 높이 변화와 저장 직전 DB의 동기화 설정·최신 체크포인트 변화를 확인하고, 바뀌었으면 새로 스캔하도록 고쳤다. 고정한 요청 순서와 양쪽 서버의 동시 동기화 요청에서도 이벤트 3건, 정산 이력 1건, 광고 잔량·버전이 유지됐다. 로컬 재구성 복구와 10,000블록 이상 따라잡기 시험도 통과했다.

열아홉 번째 검증 결과: 같은 로컬 Anvil·SQLite에서 웹 서버의 확정 블록 수를 2로 변경하고 새 주문을 진행했다. 개설·Maker 예치·정산 거래가 담긴 블록에서는 직전 상태를 유지하고 확정 이벤트·상태 이력·광고 잔량·버전을 변경하지 않았다. 다음 빈 블록을 채굴한 뒤 각각 `OPEN`, `MAKER_FUNDED`, `SETTLED`로 한 번씩 전이했고, 정산 시 광고 잔량도 한 번만 차감했다. 이 결과는 로컬 체인의 2블록 경계 검증이며 운영 체인 확정 정책 결정은 아니다.

스무 번째 검증 결과: 확정 블록 수 2에서 미확정 개설 거래와 미확정 정산 거래의 직전 체인 상태를 각각 스냅샷으로 저장했다. 거래가 담긴 블록을 되돌리고 같은 높이에 빈 블록 두 개를 채굴해도 주문 상태·확정 이벤트·상태 이력·광고 재고에 사라진 거래의 효과가 남지 않았다. 같은 주문을 다시 개설·정산해 확정한 뒤에는 `OPEN`, `MAKER_FUNDED`, `SETTLED` 이력이 각각 한 번이고 광고 잔량이 한 번만 차감됐다. 로컬 Anvil 재구성 시험이며 운영 체인의 재구성 위험 수준을 뜻하지 않는다.

스물한 번째 검증 결과: 확정 블록 수 2에서 이미 `SETTLED`로 투영된 정산 블록과 그 확인 블록을 되돌리고, 같은 높이에 다른 해시의 빈 블록을 만들었다. 인덱서는 정산 이벤트를 제거하고 주문을 `MAKER_FUNDED`로 복구했으며 광고 총량을 차감했던 0.04 ETH만큼 되돌렸다. 다른 정산 주문은 유지되고, 재구성 상태 이력이 한 번 기록됐다. 다시 정산해 확정하면 광고 총량이 정확히 한 번 차감됐다. 이 검증은 확인 블록 수를 정해도 더 깊은 재구성에 대한 운영 정책이 필요함을 보여준다.

스물두 번째 검증 결과: 총량 0.04 ETH 광고의 첫 주문을 온체인 취소해 풀린 수량을 다른 지갑이 전부 예약한 뒤, 확정됐던 취소 블록을 재구성으로 제거했다. 첫 주문을 다시 `OPEN`으로 투영하면 광고 가용량이 음수가 되므로 인덱서는 503 재고 충돌을 반환하고 로그·체크포인트·주문·재고 변경을 모두 롤백했다. 경쟁 예약자는 자기 예약을 취소할 수 있었고 원래 주문자는 대신 취소할 수 없었다. 경쟁 예약이 해제된 뒤 재동기화하자 첫 주문이 `OPEN`으로 복구되고 가용량은 0이 됐다. 충돌 중에는 저장된 취소 상태가 임시로 표시되고 체인 주문 조회가 503을 반환하므로 운영 환경에는 조정 절차가 필요하다.

스물세 번째 검증 결과: 같은 재고 충돌을 다시 만들고, 다른 지갑의 경쟁 예약 응답 기한을 테스트 DB에서 지난 시각으로 설정했다. 주문 조회가 만료를 한 번 기록하며 0.04 ETH를 광고 가용량에 반환했고, 다음 체인 동기화가 원래 주문을 `OPEN`으로 복구하면서 가용량을 다시 0으로 맞췄다. 반복 조회에서도 만료·재구성 이력과 광고 버전이 중복 증가하지 않았다. 실제 15분 경과 대신 임시 DB 시각을 조정한 로컬 통합 시험이다.

스물네 번째 개발 결과: 조회 요청 없이 예약·수락 주문과 광고의 기한을 처리하는 독립 작업 프로세스를 추가했다. 같은 SQLite DB를 사용하는 작업 프로세스 둘을 실행해 만료 이후 재고와 상태 이력이 한 번만 변경되는지 검사했다. 작업은 시작 즉시 실행되고 이후 기본 30초 간격으로 반복하며, 실패한 주기는 다음 주기에 재시도한다. 웹 서버와 함께 별도로 실행·감시해야 하고 로컬 체인 로그 동기화는 수행하지 않는다.

스물다섯 번째 검증 결과: 확정된 온체인 취소가 깊은 체인 재구성에서 사라지고 그 사이 경쟁 예약이 전량을 점유해 503 재고 충돌이 난 상태를 다시 만들었다. 독립 만료 작업을 실행하고 경쟁 예약의 응답 기한을 임시 DB에서 지난 시각으로 설정했다. 웹 조회 없이 작업이 경쟁 예약을 `EXPIRED`로 만들고 0.04 ETH를 광고 가용량에 반환했으며, 이때 원래 주문과 체인 체크포인트는 그대로였다. 이후 명시적 체인 동기화가 원래 주문을 `OPEN`, 가용량을 0으로 복구했다. 작업의 반복 주기와 동기화 재실행에도 만료·재구성 이력과 재고 변경은 중복되지 않았다. 독립 작업은 체인 동기화를 자동 실행하지 않는다.

스물여섯 번째 개발·검증 결과: 기존 `syncChain()`을 반복 호출하는 독립 체인 로그 작업을 추가했다. 로컬 Anvil 설정과 기존 SQLite DB를 요구하며 시작 즉시, 이후 기본 5초 간격으로 실행한다. 통합 시험에서 RPC를 차단한 동안에는 새 취소 거래가 있어도 DB를 변경하지 않았고, 연결 복구 뒤 HTTP 조회 없이 확정된 취소 로그를 반영했다. 취소 블록이 깊은 재구성에서 사라지고 경쟁 예약이 재고를 점유하자 작업은 재고 충돌을 기록하고 DB를 부분 변경하지 않았다. 만료 작업이 경쟁 예약을 해제한 뒤 다음 동기화 주기에서 원래 주문을 `OPEN`으로 복구했다. 반복 주기에도 이력·재고가 중복 변경되지 않았다. 두 작업 모두 별도 프로세스로 실행·감시해야 하며 로컬 체인 개발 프리뷰에 한정된다.

스물일곱 번째 검증 결과: 독립 체인 작업을 중지한 뒤 온체인 취소와 확인 블록을 만들고, 한 작업 프로세스를 재시작했다. RPC 프록시가 첫 작업의 이전 DB 체크포인트 기반 스캔을 중간에서 멈춘 사이 재시작한 다른 작업이 취소 이벤트와 새 체크포인트를 먼저 저장했다. 늦은 작업을 재개하고 여러 주기를 더 기다려도 광고 가용량은 0.04 ETH, 광고 버전 증가와 취소 이력은 각각 한 번이었고 확정 이벤트·체크포인트는 동일했다. 로컬 Anvil·SQLite에서 의도적으로 스캔 순서를 조정한 경합 검증이다.

스물여덟 번째 개발·검증 결과: 예약 만료와 체인 동기화 작업을 함께 실행하고 비정상 종료 시 지수 간격으로 재시작하는 감독 프로세스, JSON 상태 파일과 상태 조회 명령을 추가했다. 기존 DB를 공유하며 감독 프로세스 중복 실행은 잠금으로 막는다. 로컬 통합 시험에서 두 작업을 각각 강제 종료하자 새 PID로 재시작했고, 상태 명령은 재시작 중 종료 코드 1, 복구 뒤 0을 반환했다. 재시작 후 새 블록의 체크포인트도 갱신됐다. 감독 프로세스 자체의 재시작은 실행 환경의 서비스 관리자가 맡아야 한다.

스물아홉 번째 개발·검증 결과: 기존 SQLite DB와 체인 설정 파일의 절대 경로를 받아 systemd 사용자 서비스 유닛을 생성하는 명령을 추가했다. 유닛은 감독 프로세스가 종료되면 5초 후 재시작하고, 같은 DB와 체인 설정을 다시 전달한다. 공백·`%`가 있는 임시 경로에서 생성한 유닛을 `systemd-analyze verify`로 검증했다. 현재 개발 컨테이너의 systemd 관리자는 offline이므로 실제 서비스 활성화와 종료 후 재기동은 systemd가 실행 중인 호스트에서 확인해야 한다.

서른 번째 개발·검증 결과: Anvil·SQLite 통합 시험에서 감독 프로세스를 강제 종료하고, 서비스 유닛의 `KillMode=control-group`에 해당하는 자식 정리를 재현한 뒤 새 감독 프로세스를 시작했다. 두 작업은 새 PID로 정상화됐고 상태 명령은 장애 중 1, 복구 뒤 0을 반환했다. 새 블록의 체크포인트도 이어 갱신됐다. 컨테이너에서는 systemd 사용자 관리자를 실행할 수 없었고 일회용 systemd 이미지 생성도 컨테이너 DNS 실패로 막혀, systemd 자체의 자동 재시작은 미검증이다. 실제 호스트에서 실행할 절차를 README에 기록했다.

서른한 번째 개발·검증 결과: Supabase PostgreSQL을 저장소, Render를 웹·작업 호스팅 대상으로 정했다. 기존 동기 SQLite 저장소가 서로 다른 Render 인스턴스 간 공유되지 않는 점을 확인하고, `p2p` 사설 스키마의 초기 마이그레이션을 작성했다. 로컬 PostgreSQL 17에서 12개 테이블과 RLS, 재고 음수 방지, 중복 요청 키 제약을 검사했다. 광고 재고 1건에 16개 차감 요청을 병렬 실행한 결과 1건만 반영됐다. 실제 애플리케이션의 PostgreSQL 연결·비동기 저장소 전환과 Render 배포는 다음 단계다.

서른두 번째 개발·검증 결과: `DATABASE_URL`이 있을 때 웹 API, 관리자 화면, 예약 만료와 보존 정리 작업이 PostgreSQL 저장소를 사용하도록 전환했다. 로컬 PostgreSQL 통합 시험에서 SIWE·광고·예약·대화·신고·운영자 검토와 만료 작업을 확인하고, 두 웹 서버의 공유 세션 및 재고 1건에 대한 16개 동시 HTTP 예약 중 1건만 성공하는 것을 검증했다. 기존 SQLite 및 Anvil 회귀 시험도 통과했다. 실제 Supabase 프로젝트와 Render 배포는 아직 연결하지 않았다.

현재 상태: 개발 프리뷰. 실제 담보 확인, 운영 체인·실제 토큰 배포, KYC, 운영 채팅 인프라, 정식 분쟁 처리와 관리자 권한 관리는 미구현이다. 데모 광고와 가격은 예시다. 자산 주소나 출시 체인을 선정하지 않았다. 광고주 수락만으로 자산을 맡기거나 체결하지 않는다. 로컬 체인 거래는 테스트 토큰에만 한정된다.

에스크로의 자금 흐름과 운영 전 경계는 [설계안](testnet-escrow-design.md)에 정리했다. `contracts/`의 Foundry 테스트, `tests/chain-e2e.ts`의 로컬 체인 통합 테스트, `tests/indexer-recovery-e2e.ts`의 재시작·재처리 검증, `tests/browser-e2e.ts`의 브라우저 지갑 테스트가 있다.

## 구조와 후속 개발 순서

1. 웹: `app/`, 도메인: `lib/market.ts`, 테스트: `tests/`.
2. 운영 국가·법인, 단일 EVM 체인·승인 토큰 주소·확정 블록 수, 수수료·중재 권한, Maker-first 예치·환불 기한을 ADR로 확정한다.
3. Sepolia EOA SIWE 로그인과 브라우저 지갑의 계정·체인 변경 대응은 구현했다. 계약 지갑·WalletConnect와 운영 수준 레이트리밋·세션 관리가 남았다. 개인키는 수집하지 않는다.
4. 현재 SQLite 데모 광고·예약을 운영용 PostgreSQL 구조로 전환한다. 확정된 약정 snapshot과 원자적 수량 예약을 유지하면서 광고 만료 작업, API 레이트리밋, 체인에서 검증 가능한 재고 연동이 필요하다. 브라우저 견적은 계속 서버에서 재계산한다.
5. Foundry 에스크로와 증분 체크포인트 방식의 로컬 체인 인덱서는 시험 구현했다. 운영 전에는 토큰 실사·보안 감사·배포 승인과 확인 블록·재구성·장애 복구의 운영 정책이 필요하다.
6. 결정된 테스트넷에서 정상 교환, 동시 잔량 경합, 단방 예치 환불, 중복 이벤트, 접근 제어를 다시 검증한다. 지갑/체인 변경 이벤트, 장기 지연 거래와 가스비 사전 안내는 로컬 체인에서 시험했다. 다음 단계에는 운영용 채팅·신고 보안 정책과 정식 리스크 계층이 남아 있다. 실제 지갑 검증과 교체 거래 해시의 직접 추적, 평판·후기, 이의 제기는 이번 MVP 범위에서 제외했다.

## Phase 0에서 남은 결정

PRD D-01~08: 운영자 통제 범위, 대상 국가, 체인/토큰, 예치 순서, 중재 가능한 상태, 수수료와 dust, 개인정보/제재, 유동성 정책. 승인 기록이 생기기 전에는 미결정으로 유지한다. 이 프로토타입의 견적과 화면 검증은 Phase 1 온체인 E2E 또는 출시 검증을 대체하지 않는다.
